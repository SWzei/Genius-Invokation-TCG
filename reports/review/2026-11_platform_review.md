# 2026-11 Platform Review（D30）

> 核实日期 2026-11-14 / 15。证据来源写在每条后面：**源码**（克隆的仓库，注明提交）、**实测**（本次实际运行）、
> **接口**（对公开服务的只读请求）、**文档**（项目自己的说明）。没有核实的事项单列在 §6。

## 0. 结论

1. **能同时满足"程序化接入、完整行动记录、可复现"的只有一条路：genius-invokation 及其对战平台。**
   它是本仓库已经绑定的规则核心（`gitcg 0.21.0`），上游仍在周更，覆盖官方 v3.3.0–v7.2.0 共 36 个版本；
   它的对战平台（<https://play.piovium.org>）用同一套协议对外提供房间接口，游客无需账号即可建房、入房、收发行动。
2. **已完成接入并实测**：`envs/platform_room.py` 让仓库里任何策略（脚本、神经网络、LLM）以"远程座位"身份在平台房间里对局。
   在本地构建的上游服务端（与线上同一提交 `ce9e06c`）上跑通了脚本对脚本、GLM-5.3 对脚本两局完整对局，
   双方结果一致、零超时、零回退，并取回了服务端的完整状态日志。
3. **"真实高手对战"目前没有现成来源**：平台有真人，但没有天梯、没有匹配、没有公开的对局库，两次抽查时公开房间数都是 0；
   官方客户端没有任何对外接口。要拿到真人对局，只能**约人**在平台房间里打，或向维护者申请服务端日志。
   我没有让机器人进入线上公开房间——那需要对手与维护者同意。
4. **BetterGI 不适合做评测平台**：它靠截图识别操作官方客户端，只打 NPC，策略是固定的技能序列，不出牌、不换人，
   没有对局记录，并且自述存在封号风险。
5. **其余模拟器（LPSim、dgisim、GITCGSim、flick-ai）都已停更一年半以上**，规则停在 4.x–5.0，不能代表当前版本。

推荐：**模拟器内评测用本仓库引擎（已实现，见 Benchmark 报告）；真人评测走对战平台的私有房间**，按 §5 的步骤做。

## 3. 逐项核实

### 3.1 genius-invokation（piovium/genius-invokation）

- **维护**：上游 `main` 最新提交 `ce9e06c`，2026-11-12；本仓库 `engine.lock` 锁定的提交（`6f01d5c`，2026-10-05）之后又有 32 个提交。（源码）
- **规则**：服务端 `/api/version` 返回 `coreVersion 0.21.0`、`currentGameVersion v7.2.0`、36 个受支持版本
  （v3.3.0 … v7.2.0）。与本仓库安装的 `gitcg 0.21.0` 同一核心版本。（接口，线上与本地实例一致）
- **发行**：PyPI `gitcg` 最新 0.21.0（2026-09-24），要求 Python ≥ 3.11。（PyPI）
- **许可**：AGPL-3.0。（源码）
- **与官方的差异**：这是社区实现，不是官方规则本身；已知差异登记在知识库 R12（39 + 19 条待逐条核实）。

### 3.2 对战平台（`packages/server`，线上 <https://play.piovium.org>）

接口（源码 `rooms.controller.ts` / `rooms.service.ts`，提交 `ce9e06c`；本地实例实测）：

| 能力 | 接口 | 说明 |
|---|---|---|
| 版本与规则档 | `GET /api/version`、`GET /api/profiles` | 公开只读 |
| 房间列表 | `GET /api/rooms` | 匿名只能看到未结束、非私有、允许游客的房间 |
| 建房 | `POST /api/rooms` | 游客直接带牌组（3 角色 + 30 行动牌的 id），返回 `playerId` 与访问令牌；可设规则档、**随机种子**、先后手、计时、私有、可观战 |
| 入房 | `POST /api/rooms/:id/players` | 游客同上 |
| 事件流 | `GET /api/rooms/:id/players/:pid/notification` | SSE：`waiting` / `initialized` / `notification` / `rpc` / `oppRpc` / `error` / `ping`；`notification` 与 `rpc.request` 是 base64 的 protobuf |
| 作答 | `POST …/actionResponse` | `{id, response}`，`response` 为 base64 protobuf |
| 认输 | `POST …/giveUp` | |
| 对局日志 | `GET /api/rooms/:id/gameLog` | 完整状态日志；仅座位本人或可观战房间可取 |
| 历史对局 | `GET /api/games` | **需登录**（GitHub 账号） |

要点：

- **消息与进程内引擎完全相同**：服务端发给座位的 `Notification` / `Request` 就是 `gitcg.Player` 在本地收到的那两种 protobuf，
  所以 `envs.match.PolicyPlayer` 不改一行就能在远程房间里打。座位只收到服务端发给它的内容——这条路上不存在全量状态。
- **计时**：每步 25–300 秒，另有每回合与开局的总时间池（0–300 秒）。超时由服务端代打（宣布结束 / 取第一个候选）；
  **游客连续 3 次超时判负**。（源码 `timeoutRpc`）
- **断线**：重连后服务端会重发 `initialized` 和未答的 `rpc`，客户端按 rpc id 去重即可续上。（源码 + 实测）
- **版本偏差**：上游 `main` 在 `gitcg 0.21.0` 发版之后新增了第 6 种请求 `select_option`。已安装的 protobuf 类不认识它；
  客户端手工解码，并按服务端自己的超时默认值（选项 0）作答，同时计数。两局实测中这种请求出现 0 次。
- **对局日志**：一局 10 回合的日志约 319 KB，含规则档、起止时间、双方 id 与 186 个状态快照。（实测）
- **没有的东西**：天梯、匹配、内置 AI 对手、公开对局库、公开的机器人使用条款。

**活跃度**：2026-11-14 21:25 UTC 与 2026-11-15 06:32 UTC（北京时间周日 14:32）两次匿名请求，公开房间数都是 0。
私有房间和已开局房间不在这个列表里，所以这只说明"随时能匹配到路人"不成立，不说明平台没人用。

### 3.3 官方客户端

没有公开接口，没有对局导出。真人高水平对局只存在于客户端内与官方赛事转播里
（后者的牌组与胜负已在 `GITCG_Data` 中，没有逐步行动）。程序化操作它只能靠自动化工具，见下。

### 3.4 BetterGI（babalae/better-genshin-impact）

- **做什么**：项目自述是"帮助你轻松完成七圣召唤角色邀请、每周来客挑战等 PVE 内容"。（README）
- **怎么做**：OpenCV 模板匹配识别 1920×1080 画面（33 张模板图），模拟鼠标操作。（源码 `GameTask/AutoGeniusInvokation`，提交 `cc3099a`，2026-11-12）
- **策略能力**：策略文件是一串"角色 使用 技能N"。行动枚举里只有 `UseSkill` 可用，"出战"和"切换"两种指令在解析时直接抛异常；
  没有打出行动牌的指令。自带 9 套脚本。（源码 `ActionEnum.cs`、`ScriptParser.cs`、`User/AutoGeniusInvokation/`）
- **风险**：README 原话——"理论上不会被封…但是…用户条款上明确说明第三方软件/模拟操作是封号理由之一。当前方案还是存在被检测的可能。"
- **结论**：对手是 NPC、无行动记录、不可复现、动作空间不全、有账号风险。它解决的是"日常自动清任务"，不是评测。
  把它改造成"让 AI 通过视觉打官方天梯"在技术上可以设想，但等于拿用户账号去违反用户协议，我不建议，也没有做。

**对真实上游服务端的实测**（本地构建，提交 `ce9e06c`，Node 26.12.1，内置 PGlite；规则档 `official/v7.2.0`）：

| 对局 | 结果 | 决策数 | 作答用时 中位 / 最大 | 最小剩余计时 | 回退 / 超时 / 重连 |
|---|---|---|---|---|---|
| `heuristic` 对 `expert:unyielding_geo`，种子 7，计时 300 s | 双方流一致，8 回合 | 52（专家侧） | 0.01 s / 0.03 s | 317 s | 0 / 0 / 0 |
| **`llm:glm-53-plan`（真实 GLM-5.3）** 对 `expert:unyielding_geo`，种子 11，**计时 45 s** | 双方流一致，10 回合，GLM 负 | 81（GLM 侧，其中 75 次由模型作答） | 3.6 s / 32.6 s | 57 s | 0 / 0 / 0 |

第二局说明：在 45 秒档下，GLM-5.3（低强度思考）单步最慢 32.6 秒仍在时限内；但平台允许的最短档是 25 秒，
那个档位下这一步会被服务端代打。**让模型上桌要用 45 秒以上的计时**，这是与真人约战时要事先讲明的。

没有对线上服务（play.piovium.org）做过任何写操作：只发了 `GET /api/version` 与 `GET /api/rooms`。

## 5. 推荐方案

1. **日常评测：模拟器内 Benchmark**（本仓库引擎 + 固定牌组 / 对手阶梯 / 场景集）。可复现、便宜、可大量重复。它回答"在这个模拟器里对这些对手有多强"。
2. **真人评测：对战平台私有房间约战**。流程：
   - 征得对手同意，说明对面是 AI、使用哪个模型、每步可能思考数秒到数十秒；
   - `python -m scripts.platform_play host --server https://play.piovium.org --deck <牌组> --policy <spec> --seed <n> --action-time 60`，把房间号发给对手；
   - 结束后 `data/platform/<tag>/` 里有结果、逐事件留痕和服务端状态日志，可回放、可审计；
   - 同一对手同一牌组换先后手各打若干局，按配对口径报告，样本量与置信区间照 Benchmark 的写法。
   这回答"对这几位真人有多强"，样本天然很小，不能外推成"天梯水平"。
3. **向维护者申请**两件事：是否允许标明身份的机器人进入公开房间；能否提供脱敏的历史对局日志（服务端保存了完整状态）。
   后者是获得"真实高手完整行动记录"的唯一现实来源。
4. **不做**：通过 BetterGI 或类似工具让 AI 操作官方客户端。

## 6. 没有核实的事项

- 平台的真实用户量、对局量、用户水平分布——没有公开数据，我也没有登录查看。
- 平台维护者对机器人的态度——仓库与前端里没有找到相关条款；没有询问。
- 线上服务端对长时间对局、网络抖动的实际表现——只在本机实例上测过，线上未连。
- 其他闭源或小范围的社区平台、群内机器人——通用网页检索没有发现；检索不到不等于不存在。
- 各模拟器与官方规则的逐条差异——只核对了它们自述的覆盖范围。
