# 知识接入的分阶段优化

> 日期 2026-11-21（太平洋时间 15:50–22:40；UTC 11-21 23:50 至 11-22 06:40，周末，全部在 DeepSeek 非高峰时段）。
> 环境：云端 2 核 / 8 GB，`gitcg 0.21.0`。模型 `deepseek-flash`（V4.1-Flash，非思考，温度 0）。
> 知识库 `GITCG_KB` v1.0，**内容一字未改**；本轮只改"知识怎么在决策时被选出来、怎么被用"。
> 所有对局与场景都在模拟器内，不代表真人竞技水平，不进强度验收（D1）。

## 0. 结论

1. **有明显进步，来源是两处接入层改动的组合**：按可见局面触发对应规则节（S4），再让模型先写依据后作答（S5）。
   在保留的 test 划分上（只跑一次）：
   - 情境规则题（260 题 × 2 轮）：**0.923**，无知识 0.812、原接入 0.840；对无知识 **+0.112 [+0.074, +0.149]，39 好 / 2 差，p < 0.001**。
   - 整局 `lite`（56 格；S5 两轮 112 局）：**0.821**，无知识 0.747（三轮）、原接入 0.777（两轮）；
     对无知识逐格 **+0.074 [+0.007, +0.141]，11 好 / 4 差，p = 0.118**。三档对手上都更高（对脚本专家 0.562 对 0.396），
     但按格的符号检验还不显著。
   - 斩杀转化（70 题 × 2 轮）：0.936，与无知识 0.943 持平。dev 上 S5 的 +0.055 **没有在 test 上复现**。
     原接入在 test 上**显著更差**（−0.064，0 好 / 7 差，p = 0.016），S5 把这部分损失补了回来。
2. **原接入的问题不在知识库内容，而在"给到"与"用上"两步**（train 上的错误分析，dev / test 复核）：
   - **给不到**：局面需要的规则节几乎从不被注入。反应题注入附着转移表 0/80，召唤题注入召唤区上限 0/80。
   - **给错**：通用规则"战斗行动后轮到对方"在对方已宣布结束时误导模型。这类题的正确率从无知识的 78/80 降到 70/80。
   - **给了不用**：直接作答时，给出了骰子奇偶规则，"重击"题仍只对 6/34。要求先写依据后，同样的题基本都对。
     对局里的 LLM 玩家原先的回复格式是先给选项、后写理由，等于"直接作答"。
3. **三个看上去合理的改动没有带来可测收益**：规则按决策文本做 BM25 检索（S1）、剪掉在训练集上触发过宽的策略单元（S2）、
   针对"斩杀窗口"的定向资料（S3）。它们在 train 和 dev 上都在噪声内，S1 在 dev 上甚至略差（−0.031，p = 0.027）。
   定向资料也没有阻止 test 上的同类错误（§5.2）。
4. **只改回复格式、不加知识没有用**：先写依据但无知识，在斩杀上 0.898，与直接作答 0.922 无差别；
   在情境题上 +0.05。两者合起来才有效：S5 对 S4 在斩杀 dev 上 6 好 / 0 差（p = 0.031）。
5. **方法与工具**：
   - 场景集 v2 按源对局种子固定划分 train / dev / test。
   - 新指标：斩杀新增 `converted`（继续打完本轮并赢下）和 `kept`；新增情境规则题，答案由程序按规则表算出。
   - 新增阶段报告与多轮整局合并工具。
   - 修了两处会让长任务卡死或崩溃的问题：Python 3.12.3 进程池换进程死锁；连接中途断开未被当作网络错误重试。
6. **花费 34.15 元**（余额 87.57 → 53.42），按调用日志估算约 5.1 美元。其中整局约 4 美元。

## 1. 设计

### 1.1 数据纪律

| 数据 | train | dev | test | 用途 |
|---|---|---|---|---|
| 场景集 v1（40 局源对局，52 道斩杀） | 全部 | — | — | 错误分析、策略单元频次表 |
| 场景集 v2（160 局源对局，219 道斩杀，按种子固定划分） | 59 局 / 85 题 | 49 局 / 64 题 | 52 局 / 70 题 | 阶段比较在 dev；test 选定后只跑一次 |
| 情境规则题 `situ_d32`（每局源对局取 1 个行动决策 × 5 题） | 495 题（其中 v1 的 200 题用于本轮训练分析） | 245 题 | 260 题 | 同上 |
| `lite` 整局 56 格（D30 起的保留种子） | — | — | 全部 | 只评最终配置 |

拟合与分析只看 train：错误归类、频次表、触发规则的设计。阶段取舍只看 dev。test 与整局在选定 S5 后才跑，各跑一次，没有据此再改任何东西。

### 1.2 两套主指标

- **情境规则题**（主敏感指标）：从真实对局的决策点取局面，问一道必须结合局面和规则才能回答的题。共五类：
  重击奇偶、元素反应、行动权、宣布结束之后、召唤区余量（`docs/howto/benchmark.md` §7.3）。
  标准答案由程序从可见状态和知识库规则表算出；1,000 题的答案已用另写的一份规则表逐题复核，0 处不符。
  **知识按决策局面选取，不看题目**（与对局里同一段代码），所以它测的是"决策时注入的知识里有没有、用没用上这条规则"。
  每题同时记录注入的知识是否包含所需规则节。
- **斩杀转化**（守门指标）：从斩杀局面起让模型继续打完本轮（最多 6 个己方决策），在对方行动前赢下才算。
  旧口径"这一步就选中立即获胜的选项"会把"先打一张免费牌再斩杀"判错（v1 上 52 题中约 5 道误判）。
  新口径在 v1 上无知识已有 0.92，接近天花板，所以只用来防止改动伤害斩杀。

### 1.3 阶段

| 阶段 | 改动 | 依据（train） |
|---|---|---|
| S0 | 原接入（`rules-strategy`）：规则按行动类型固定映射，策略单元按检测器 | D31 基线 |
| S1 | S0 的规则改为 BM25 检索，查询 = 合法选项 + 公开局面；排除不描述玩法的 R00 / R11–R13 | D31：固定映射只覆盖 11/90 节 |
| S2 | S1 + 剪掉在 train 行动决策上触发 > 50% 的策略单元；每次最多 2 个 | 频次表：S04-P1 80%、S02-P1 73%、S06-P4 70%、S02-P5 68%、S01-P7 56% |
| S3 | S2 + "斩杀窗口"定向资料，只在对方仅剩 1 名角色且 ≤ 5 血时注入 | v1 斩杀失误 15 题：约 8 题是没算到结束阶段召唤物伤害 |
| S4 | S3 + 情境触发规则节：对方已宣布结束 → R03 §3、R01 §4.3；对方出战角色有附着 → R06 §2、§3.1；我方召唤物 ≥ 3 → R07 §1；可用技能 → R04 §3。触发的优先，其余按检索补足，最多 4 节 | 情境题 train：所需规则几乎从不注入；R03 §1 在对方已结束时误导 |
| S5 | S4 + LLM 回复格式先写依据（局面数字与规则）再给选项（`reply=reason_first`） | 情境题 train：直接作答时给了规则也不用；先写依据时 +0.105 |

## 3. 改了什么在起作用

**注入覆盖**（`reports/bench/kb_probe_kbt.md`；`lite` 56 格，启发式打完整局，每个决策点调用与对局相同的选取代码）：

| 配置 | 不同规则节 | 不同规则组合 | 不同策略单元 | 有策略的决策 | 平均字数 |
|---|---|---|---|---|---|
| S0 | 11 | 11 | 14 | 4,202 / 4,350 | 1,611 |
| S1（检索） | 19 | 181 | 14 | 4,202 / 4,350 | 1,811 |
| S2（+ 剪枝） | 19 | 181 | 9 | 3,671 / 4,350 | 1,444 |
| S4（+ 触发） | 25 | 377 | 9 | 3,671 / 4,350 | 1,858 |

- 检索让规则组合从 11 种变成 181 种，但选中最多的仍是通用章节：R03 §2 五种基本行动 2,839 次，R03 §1、R01 §4.2 各约 2,200 次。
  附着转移表 R06 §2 只有 139 次，所以单靠检索补不上局面需要的规则。
- 触发规则把 R06 §2 / §3.1 提到约 1,480 次，R01 §4.3 结束阶段提到 1,128 次，规则组合达到 377 种。
  选中哪些规则，开始跟着局面内容变，而不只跟着"有哪些行动类型可选"变。
- 本表不含 S3 / S4 的"斩杀窗口"资料，体检工具只统计规则与策略单元。

**情境题的分解**说明收益集中在哪里（test，先写依据）：

| 题型 | 无知识 | S4 | 说明 |
|---|---|---|---|
| 重击（骰子奇偶） | 43/104 | 78/104 | 模型不知道这条规则；给了规则且要先写依据才会用 |
| 行动权（对方已结束时） | 95/104 | 102/104 | S0 降到 76/104：通用规则误导；S4 在对方已结束时补上 R03 §3 |
| 元素反应 | 88/104 | 99/104 | 附着转移表与反应加成；S4 在对方有附着时注入 |
| 召唤区余量 | 92/104 | 97/104 | 触发条件（≥ 3 个召唤物）在样本里很少成立，注入 2/104，提升主要来自其它 |
| 宣布结束之后 | 104/104 | 104/104 | 天花板 |

**斩杀上 S0 为什么更差**（test 上 S0 失手而无知识拿下的 7 题）：多数是把斩杀回合用来铺垫，例如"战技召唤雷眼，持续输出"。
理由文本与 S0 注入的策略观点一致，比如充能兑现、抢先结束。
S5 在其中 6 题上两轮都拿下。S5 比无知识差的 4 题里，两题见 §5.2。

## 4. 修复

| 问题 | 现象 | 修复 |
|---|---|---|
| Python 3.12.3 `ProcessPoolExecutor(max_tasks_per_child=…)` 换进程死锁（CPython gh-115634） | 频次统计与题库生成静默挂起，没有工作进程 | `common/pool.recycled_map`：分批、每批新建进程池；`bench.kb_train`、`bench.kb_situ`、`bench.kb_probe`、`bench.scenarios keep` 改用 |
| 连接在响应中途断开（`http.client.IncompleteRead`） | 情境题评测崩溃 | `common/llm_providers` 把 `HTTPException` 归为网络错误并重试；加了测试 |
| 场景集生成不可续跑 | 240 局生成跑满 2 小时后台上限被停，结果全丢 | 每局完成即写入 `data/bench/scen_build_<name>.jsonl`，重跑从断点继续 |
| 知识库自带检索对中文无效 | 中文问句 53/56 返回空 | `KnowledgeBase.search` 在空格切词无命中时回退到二元字 BM25（规则问答前 3 命中 0 → 0.893） |

## 5. 局限与下一步

### 5.1 局限

- **整局的提升还没有统计确认**：p = 0.118，区间下沿 +0.007。按格的检验要显著，大约还需要 S5 再跑 2 轮、无知识再跑 1 轮，
  约 170 局、16 元。这超出本轮估算，没有擅自运行。
- **情境题与 S4 的触发规则出自同一人之手**：触发条件是看了 train 上的题型后设计的，所以情境题上的提升有"对题设计"的成分。
  不依赖这份设计的证据是 dev / test 的斩杀与整局。在这两项上，S5 一项持平（test 斩杀）、一项为正向趋势（整局）。
- **斩杀转化在 test 上没有提升**：dev 上 S5 4 / 0 的优势没有复现，test 上为 4 / 4。
  在保留数据上能确认的只有"S5 不伤害斩杀、并修复了 S0 的伤害"。
- **"只改回复格式"没有在整局上单独测**（只在斩杀和情境题上测了），所以整局上 S5 的提升里先写依据与触发规则各占多少，目前分不开。
- 单模型（DeepSeek-V4.1-Flash 非思考）；S5 每次输出 token 约 57（原 36），决策延迟中位 1.47 s（原 1.13 s），每局费用约为无知识的两倍。

### 5.2 test 上看到、但本轮不据此改动的失误

test 只用于报告，所以这里只记录现象，留给下一轮在 train / dev 上验证：

- `lethal-0126`：对方**未**宣布结束，S5 写出"直接宣布结束，结束阶段召唤物伤害可击倒"，宣布后对方继续行动。
  定向资料里写了这一点（"对方未结束时仍能行动"），但触发规则只在对方**已**结束时注入 R03 §3。
  未结束时的行动权规则是下一轮的候选。
- `lethal-0059`：多步计算前后不一致。第一步算出"粉碎之冰 +2 后可斩杀"，下一步又写"不足斩杀"。

### 5.3 下一步建议

1. 若要确认整局收益：S5 再跑 2 轮、无知识再跑 1 轮（约 16 元）。可以再加一组"只改回复格式"，用来拆开两者的贡献。
2. S1–S3 在本轮无收益，但仍包含在 S4 之下。可以做一次消融：以 S0 为底只加触发规则与先写依据，
   看能否在更少 token 下得到同样效果。
3. 把触发规则补全到"对方未宣布结束""己方已宣布结束"等反面情形；并把规则节改写成短小、可直接套用的"规则卡"，
   以减少 S4 每次约 2,900 token 的输入。
